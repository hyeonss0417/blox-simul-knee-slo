Executive Summary
기존 GPU 스케줄러는 추론 SLO를 체계적으로 위반하며, 비대칭 스코어링이 이를 해결한다
학습(training)에 최적화된 기존 정책을 추론(inference)에 그대로 적용하면, 응답 시간 보장(SLO)이 무너진다. SLO 마감일 기반의 비대칭 가중치로 긴급 작업을 즉시 처리한다.
문제

추론은 짧은 실행시간과 엄격한 SLO를 요구하나, FIFO/SRTF/LAS는 "언제까지 끝나야 하는가"를 전혀 고려하지 않는다.

접근

SLO 마감까지의 여유(slack)를 비대칭 스코어링한다. 위반 임박 시 10× 가중치로 즉시 우선 실행하고, 배치 정책과 공동 최적화한다.

검증

Blox 시뮬레이터 위에 4종 스케줄러를 구현하고, 실제 Philly Trace(117K jobs) 고부하 환경에서 SloScoring이 FIFO 대비 JCT 62% 감소를 달성했다.

So What

학습용으로 설계된 FIFO, SRTF, LAS는 "이 작업이 언제까지 끝나야 하는가"를 전혀 고려하지 않는다. 추론 워크로드에는 SLO 마감 시한을 직접 반영하는 새로운 스케줄링 기법이 필요하다.

02
Baseline Analysis
기존 세 정책 모두 SLO 개념이 부재하다
각 정책은 고유한 장점이 있으나, 추론의 핵심 요구인 "마감 준수"를 충족하지 못한다.
FIFO
First-In First-Out
먼저 제출된 작업을 먼저 실행한다. 구현이 간단하고 공정하다.
A(10hr) → B(1min) → C(30s)
B, C는 10시간 대기
Head-of-Line Blocking
SRTF
Shortest Remaining Time First
남은 시간이 가장 짧은 작업부터 실행. 이론적으로 평균 JCT 최적해.
실제 환경에서는 남은 시간을
미리 알 수 없으며,
긴 작업이 무한히 밀린다
Oracle Baseline 기아 문제
LAS
Least Attained Service
가장 적게 서비스받은 작업 우선. 실행 시간을 몰라도 적용 가능.
짧은 작업이 자연히 우선 처리
하지만 SLO 마감 개념 없음
SLO 무관
Gap

세 정책 모두 작업의 긴급도(urgency)를 판단하지 못한다. 추론 환경에서는 "아직 여유 있는 작업"과 "곧 마감인 작업"을 구분하는 메커니즘이 필수적이다.

04
Proposed Method
위반 임박 시 급격히, 여유 시 완만하게 — 비대칭이 핵심이다
SLO 마감까지의 여유(slack)를 비대칭 함수로 스코어링하여, 긴급 작업을 즉시 처리한다.
Core Algorithm
비대칭 스코어링 함수
Slack이란? 작업이 SLO 마감까지 남은 여유 시간.
양수 = 여유 있음, 음수 = SLO 위반 임박
† SLO deadline = 예상 완료 시간 × 2.0
1. Slack 계산
slack = deadline − (now + remaining)
2. 비대칭 스코어링
slack < 0 score = −10.0 × |slack| slack ≥ 0 score =   1.0 ×  slack
3. 실행 순서
score가 낮을수록 먼저 실행
α = 10.0  위반 페널티 (급경사)
β  = 1.0  여유 보상 (완경사)
α >> β  이 비대칭이 SLO 보호의 핵심

Core Implementation
SloScoring 핵심 코드
class SloScoring(SchedulingPolicy): alpha = 10.0 # SLO 위반 가중치 beta = 1.0 # 여유 가중치 def schedule(self, job_dict, ...): for job in job_dict.values(): deadline = job["submit_time"] + 2.0 * job["duration"] slack = deadline - (now + job["remaining"]) if slack < 0: job["score"] = -self.alpha * abs(slack) else: job["score"] = self.beta * slack return sorted(jobs, key=lambda j: j["score"])

Analysis
정책 간 차이 해석
1. FIFO: Head-of-line blocking
긴 작업이 GPU를 점유하면 뒤의 짧은 작업이 94,709초(26시간) 대기. 응답성 최악.
2. LAS: Preemption 역설
짧은 작업은 즉시 시작(441s)하지만, 긴 작업의 반복 preemption으로 P99 JCT가 4,615,936초로 폭증.
3. SloScoring: 최적 균형
SRTF급 JCT + LAS급 응답성을 동시 달성. SLO 마감 기반 우선순위가 Oracle 수준 성능을 비Oracle 방식으로 구현.
So What

SloScoring은 작업 소요시간을 미리 알 필요 없이(non-Oracle) Oracle 수준의 JCT와 최고 수준의 응답성을 동시에 달성한다.
